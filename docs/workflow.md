# n8n Workflow

## Workflow Name

LeadFlow - Lead Intake

## Purpose

The workflow receives an inbound lead, normalizes the submitted data, analyzes the customer message using AI, and stores both the original and AI-generated information in Supabase.

## Current Workflow

Webhook
↓
Edit Fields
↓
AI - Analyze Lead
↓
Prepare Lead Record
↓
Create a Row - Supabase

---

## 1. Webhook

### Purpose

The Webhook node is the entry point of the automation.

It receives lead information from an external application through an HTTP POST request.

### Configuration

HTTP Method:

POST

Path:

lead-intake

Authentication:

None during MVP development

Respond:

When Last Node Finishes

### Example Input

{
  "name": "Mario Rossi",
  "email": "mario@test.it",
  "company": "Rossi Srl",
  "message": "Vorrei automatizzare la gestione delle fatture."
}

The webhook receives additional HTTP metadata such as headers, parameters and query information.

The relevant lead information is contained inside the request body.

---

## 2. Edit Fields

### Purpose

The Edit Fields node normalizes the incoming webhook payload.

The webhook provides the values inside:

body.name
body.email
body.company
body.message

The Edit Fields node converts them into a simpler structure:

name
email
company
message

### Mapping

name → body.name

email → body.email

company → body.company

message → body.message

### Output Example

{
  "name": "Mario Rossi",
  "email": "mario@test.it",
  "company": "Rossi Srl",
  "message": "Vorrei automatizzare la gestione delle fatture."
}

This normalized structure makes the data easier to use in subsequent workflow nodes.

---

## 3. AI - Analyze Lead

### Purpose

The AI node analyzes the free-text lead message and converts it into structured business information.

The AI receives:

message

and returns:

category
subcategory
priority
summary
next_action

### Example Output

{
  "category": "Sales",
  "subcategory": "Invoice automation",
  "priority": "medium",
  "summary": "User requests automation of invoice management.",
  "next_action": "Request more information"
}

### Classification Principles

The AI should only use information contained in the original lead message.

It should not invent missing information.

Priority values are limited to:

high
medium
low

Possible next actions include:

Schedule discovery call
Request more information
Route to support
Route to administration
Manual review

---

## 4. Prepare Lead Record

### Purpose

The AI node returns only the generated analysis.

The original lead information therefore needs to be combined with the AI-generated fields before the record is stored.

The Prepare Lead Record node creates one final normalized object.

### Final Record Structure

{
  "name": "Mario Rossi",
  "email": "mario@test.it",
  "company": "Rossi Srl",
  "message": "Vorrei automatizzare la gestione delle fatture.",
  "category": "Sales",
  "subcategory": "Invoice automation",
  "priority": "medium",
  "summary": "User requests automation of invoice management.",
  "next_action": "Request more information"
}

This object becomes the standard data structure used by the backend.

---

## 5. Supabase - Create a Row

### Purpose

The final workflow node stores the processed lead in the Supabase database.

### Table

leads

### Fields Sent by n8n

name
email
company
message
category
subcategory
priority
summary
next_action

### Fields Generated by Supabase

id

created_at

status

The default lead status is:

new

## Business Rules and Routing

After the lead has been stored in Supabase, the workflow uses an n8n Switch node called:

Route Lead

The purpose of this node is to separate AI interpretation from deterministic workflow execution.

The AI determines the category of the request.

n8n then applies predefined routing rules.

Current routing logic:

Sales
→ Update Sales Lead
→ status = sales_review

Support
→ Update Support Lead
→ status = support_review

Administration
→ Update Administration Lead
→ status = administration_review

Any unmatched category
→ Fallback
→ status = manual_review

---

## Switch Configuration

The Route Lead node evaluates:

{{ $json.category }}

Current routing rules:

Rule 1

category = Sales

Output:

Sales

Rule 2

category = Support

Output:

Support

Rule 3

category = Administration

Output:

Administration

Fallback Output:

Any category not matching the rules above.

Examples include:

- Partnership
- Other
- unexpected AI output

These requests are sent to manual review.

---

## Status Update Nodes

Each Switch output is connected to a Supabase Update Row node.

All update nodes identify the lead using its unique database ID.

Filter:

id
Equals
{{ $json.id }}

Only the status field is updated.

### Sales

status = sales_review

### Support

status = support_review

### Administration

status = administration_review

### Fallback

status = manual_review
